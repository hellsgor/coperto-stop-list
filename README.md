# Панель стоп-листа кухни

Тестовое задание для позиции Middle Frontend (React / Next.js) в Coperto.

## Задача

Один экран для менеджера зала: список позиций меню смены с фильтрами по цеху и статусу, постановка позиции в стоп-лист (с причиной и сроком) и снятие с него. Изменение статуса происходит оптимистично — сразу на экране, без ожидания ответа сервера, — а мутации сервера иногда завершаются ошибкой, после которой строка откатывается к прежнему состоянию.

Данные отдаёт мок-бэкенд на route handler'ах Next.js с искусственной задержкой и случайными сбоями, имитирующими нестабильную сеть.

## Стек

Next.js (App Router, Turbopack), React, TypeScript (strict), Tailwind CSS, TanStack Query, Zustand, React Hook Form + Zod, `motion`, Jest + Testing Library.

## Запуск

```bash
npm install
npm run dev
```

Приложение поднимется на [localhost:3000](http://localhost:3000). Установка и запуск не требуют сети сверх `npm install` — шрифт захостен в репозитории (см. «Ключевые решения»).

Остальные скрипты:

```bash
npm run build      # продакшен-сборка
npm run start      # запуск собранного приложения
npm run lint       # eslint
npm run typecheck  # tsc --noEmit
npm test           # jest
npm run format     # prettier --write
```

Отладочный режим ошибки списка: `http://localhost:3000/?debug=fail` — `GET /api/menu-items` всегда отвечает `500` и повторные запросы отключены, чтобы можно было спокойно посмотреть состояние ошибки.

## Архитектура

```text
src/
  app/                 # роутинг и композиция, минимум логики
    layout.tsx         # шрифт (self-hosted Inter), Providers — server component
    page.tsx           # server component: prefetch списка → HydrationBoundary
    loading.tsx        # server: скелет списка на время стриминга
    providers.tsx      # 'use client': QueryClientProvider, MotionConfig
    fonts/             # inter-variable.woff2 (self-hosted Inter) + OFL.txt
    api/menu-items/... # route handlers: тонкие, валидируют и вызывают server/menu-store
  features/stop-list/
    api/               # функции транспорта (fetch) — единственное место, знающее URL
    model/             # queries (ключи кэша), мутации, схемы, фильтры, ui-store
    ui/                # компоненты фичи ('use client')
    lib/               # чистые хелперы фичи (форматирование, парсинг времени)
  shared/
    ui/                # Button, Select, Badge, Spinner, Toast — без знания домена
    api/               # http-клиент, ApiError
    lib/               # get-query-client и прочие общие утилиты
  server/              # только для route handlers: in-memory хранилище, сид
  types/               # доменные типы и контракт ошибки API
```

Направление импортов: `app → features → shared/types`. Модули `shared` не импортируют ничего из `features`. `server/` импортируется только из `app/api/**` — клиентский код о хранилище ничего не знает.

Работа с данными вынесена из UI: запросы и мутации живут в `features/stop-list/api` и `model`, ключи кэша описывает только фабрика `menuKeys`. Компоненты в `features/stop-list/ui` не вызывают `fetch` и не импортируют `api/` напрямую — данные и колбэки получают через хуки из `model/`.

## Граница server/client

- **Server-компоненты (по умолчанию):** `app/layout.tsx` и `app/page.tsx`. `page.tsx` помечен `export const dynamic = 'force-dynamic'`, на сервере прогревает `QueryClient` через `prefetchQuery` и передаёт кэш клиенту через `HydrationBoundary`. Сами фильтры на сервере не парсятся — фильтрация полностью клиентская.
- **Клиентская граница** начинается с `app/providers.tsx` (`QueryClientProvider`, `MotionConfig`) и `StopListView` — самого верхнего компонента фичи, которому нужны `useSearchParams`, TanStack Query хуки и интерактивность. Всё под ним (`Filters`, `StopListTable`, `StopReasonPanel`, `ToastViewport`) — тоже клиентские, `'use client'` стоит на самом нижнем уровне, где это действительно нужно.
- **Route handlers** (`app/api/menu-items/**`) — единственное место, откуда импортируется `server/menu-store.ts`. Они тонкие: валидация через общую Zod-схему, вызов стора, ответ через `jsonOk`/`jsonError` с `Cache-Control: no-store`.

## Ключевые решения

| Вопрос | Решение |
| --- | --- |
| Где фильтровать | На клиенте: один запрос `GET /api/menu-items`, один ключ кэша, фильтрация через `select`. Позиций всего 12–15, а один кэш делает оптимистику и откат тривиальными |
| Фильтры в URL | `useSearchParams` + нативный `window.history.pushState`, а не `router.push` — не гоняет серверный ре-рендер `page.tsx` на каждый клик, но кнопка «назад» по-прежнему работает |
| Оптимистика | Правится и откатывается только одна строка (не снимок всего списка), инвалидация кэша ждёт, пока в полёте нет других мутаций |
| Пометка «сохраняется» | `useMutationState` по pending-мутациям — серверное состояние не дублируется в сторе |
| Zustand | Только UI-состояние: открытая панель, выбранная позиция, очередь тостов |
| Валидация | Одна Zod-схема (`stopItemSchema`) — используется и в React Hook Form, и в route handler'е |
| Редактирование стопа | Тот же `POST /:id/stop` с семантикой upsert — форма сама переключается в режим редактирования по текущему статусу позиции |
| Анимации | Пакет `motion` (бывший Framer Motion), `MotionConfig reducedMotion="user"` уважает `prefers-reduced-motion` |
| Шрифт Inter | Самостоятельный хостинг через `next/font/local` вместо `next/font/google` — сборка не должна зависеть от доступности `fonts.googleapis.com` в момент `npm run dev`/`build`. `src/app/fonts/inter-variable.woff2` — официальный вариативный Inter из [google/fonts](https://github.com/google/fonts), засабсеттирован `pyftsubset` под те же диапазоны юникода `latin` + `cyrillic`, что обычно отдаёт сам Google; лицензия SIL OFL 1.1 лежит рядом в `src/app/fonts/OFL.txt` |

## Допущения

В ТЗ эти места не были уточнены явно:

1. **Редактирование позиции в стопе** — тот же upsert-эндпоинт `stop`, отдельного эндпоинта для редактирования нет.
2. **Истёкший срок `until`** — сервер лениво снимает просроченные стопы при чтении: позиция возвращается в продажу, если остаток больше 0, иначе остаётся в стопе с пометкой «срок истёк».
3. **Конец смены** — модели смены нет, `until: null` это только подпись «до конца смены», снимается вручную.
4. **Ошибка загрузки списка** — в ТЗ случайные ошибки заданы только для мутаций, поэтому добавлен отладочный параметр `?debug=fail`, чтобы состояние ошибки можно было посмотреть на превью.
5. **Гонки на одной строке** — пока по позиции идёт мутация, её кнопки заблокированы; мутации разных строк идут параллельно и откатываются независимо.
6. **Часовой пояс** — время вводится и показывается в локальном поясе браузера, на сервер уходит ISO в UTC.
7. **Стоп при нулевом остатке** разрешён, ограничение касается только снятия со стопа.
8. **Граница «сейчас» между клиентом и сервером** — время, выбранное впритык к текущему моменту, может пройти клиентскую проверку и не пройти серверную; в этом случае пользователь видит тост с ошибкой, строка откатывается.

## Поведение на Vercel

- Хранилище (`server/menu-store.ts`) — in-memory, состояние живёт в `globalThis` **одного** serverless-инстанса. На Vercel это значит: сид пересоздаётся при холодном старте, а несколько инстансов не видят изменения друг друга — стоп-лист может выглядеть так, будто «забывает» изменения между запросами. Это ожидаемо для тестового задания без настоящей БД.
- Искусственные задержки (800 мс на список, 600 мс на мутации) и ~20% случайных ошибок мутаций сохраняются и в проде — это часть требований ТЗ, не баг.
- Серверный prefetch в `page.tsx` резолвит базовый URL для собственных API-запросов через `process.env.VERCEL_URL`, поэтому на Vercel он работает без дополнительной настройки переменных окружения.

## Что бы доделал

Технический долг, накопленный за вехи разработки (не блокирует критерии приёмки):

- `http()`-клиент: ошибка сети или нераспарсенное тело ответа всегда маппится на код `SIMULATED_FAILURE`, хотя причина может быть другой.
- Успешный ответ `http()` не валидируется Zod-схемой на клиенте — доверяем контракту route handler'а.
- `catch` в `http()` не пробрасывает `cause` и не отличает отменённый запрос (`AbortError`, например при `cancelQueries`) от настоящего сетевого сбоя.
- Резолвер React Hook Form в `StopReasonPanel` мапит только issues по полям `reason`/`until` — root-issues схемы вне этих полей терялись бы молча (сейчас недостижимо: в схеме таких issues нет).
- Панель стопа закрывается и при ошибке мутации, не только при успехе — данные формы теряются, но откат строки и тост это компенсируют.
- `role="status"` висит на самом тосте, а не на постоянном контейнере — теоретический edge case для скринридеров в момент исчезновения тоста.

За пределами ТЗ сознательно не делали: реальный бэкенд и БД, авторизацию, несколько страниц, поиск/сортировку/пагинацию, историю изменений, мобильную адаптацию, pixel-perfect вёрстку.
